03. Recomendaciones de Arquitectura & Base de Datos

3.1. Inmutabilidad de Pagos e Historial de Precios (Auditoría Contable)

En un gimnasio, los precios de las membresías cambian a lo largo del año por inflación o políticas comerciales. Si se actualiza el precio del plan Full Access de \$22.000 a \$26.000 en el backend, los pagos pasados o las cuotas emitidas con anterioridad no deben recalcularse retroactivamente.

Recomendación para la BD: La tabla pagos debe almacenar explícitamente: monto_cobrado (DECIMAL), precio_plan_momento (DECIMAL), periodo_mes ("YYYY-MM"), metodo_pago y fecha_pago (DATE). No debe confiarse únicamente en un JOIN dinámico a la tabla planes para saber cuánto costaba el pase en meses anteriores.

3.2. Reglas de Asistencia: Control Anti-Fraude vs. Doble Turno

El control implementado en el frontend bloquea más de un ingreso el mismo día calendario. Al diseñar el backend, la lógica recomendada es:

  • Regla por defecto (98% de los casos): Impedir nuevo check-in si existe un registro para el socio con fecha = CURRENT_DATE y la sesión previa tiene menos de 100 minutos de antigüedad (sesión activa en sala).
  • Excepción para doble turno: Si el gimnasio incorpora socios con pases especiales de doble turno (ej: mañana musculación y tarde spinning), el backend puede permitir un segundo check-in únicamente si la sesión anterior ya ha superado los 100 minutos (timestamp < NOW() - INTERVAL '100 minutes') y el plan lo habilita.
  • Índice en BD: Crear índice compuesto CREATE INDEX idx_asistencias_alumno_fecha ON asistencias (alumno_id, fecha); para que la verificación en el tótem responda en menos de 5 milisegundos.

3.3. Autenticación y Control de Accesos Basado en Roles (RBAC + JWT)

Actualmente el frontend bifurca rutas en el cliente mediante AppShell y puedeAccederRuta. En el backend, la seguridad debe ser infalible a nivel API:

  • Tokens JWT sin estado: El token de sesión debe contener { sub: usuario_id, rol: "ADMIN" | "ALUMNO", alumno_id: string | null } firmado con secreto seguro (HS256 o RS256).
  • Protección de endpoints por Guard/Middleware:
    • POST /api/pagos, PUT /api/planes, DELETE /api/alumnos/:id → Exclusivos para rol ADMIN.
    • GET /api/mis-cuotas, GET /api/mi-rutina → Autolimitados al req.user.alumno_id para evitar fuga de datos entre socios.
    • POST /api/asistencias/totem → Endpoint protegido por API Key dedicada o token de dispositivo exclusivo de la tablet de recepción.

3.4. Sincronización en Tiempo Real (De BroadcastChannel a WebSockets / SSE)

En la versión local actual utilizamos BroadcastChannel y StorageEvent, lo cual sincroniza perfectamente diferentes pestañas del mismo navegador. Al pasar a producción en red:

Opción A: Server-Sent Events (SSE)

Unidireccional servidor → navegador. Ideal para el panel de Asistencias y Aforo. Extremadamente liviano, reconexión automática nativa en HTTP/2 sin overhead.

3.5. Transacciones ACID e Idempotencia en Cobros y Check-ins

En operaciones concurrentes (por ejemplo, dos recepcionistas cobrando al mismo tiempo o un socio ingresando mientras se procesa su pago):

  • Transacciones atómicas: El cobro de una cuota y la actualización del estado del socio deben ejecutarse dentro de un bloque BEGIN ... COMMIT para evitar que un fallo de red deje un pago registrado sin actualizar la cuenta del alumno.
  • Claves de Idempotencia: En el endpoint de cobro, aceptar un encabezado X-Idempotency-Key generado por el cliente. Si la recepcionista hace doble clic accidental en "Guardar pago", la API rechazará el duplicado.
